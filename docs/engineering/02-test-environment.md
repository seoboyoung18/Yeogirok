## 데이터

`performance-tests/fixtures/seed-footprints-tips.sql` 로 만든다. 난수 씨앗을 고정해 같은 건수면 같은 데이터다.

| 항목 | 값 |
|---|---|
| 규모 | 발자취·AR 팁 각 1천 / 1만 / 10만 / 100만 건 |
| 회원 | 건수 / 20 (최소 100명). 한 사람당 발자취 평균 20건 |
| 위치 | 60% 는 도시 12곳 주변(중심에서 대략 ±0.15도), 40% 는 한국 범위에 고르게 |
| 시각 | 최근 365일에 고르게 |
| 상태 | 발자취 5% 삭제. 팁 90% PUBLISHED, 7% FAILED, 3% DELETED |
| 카테고리 | 발자취마다 8개 중 1~3개 |

운영 데이터(2026-11-16 기준 발자취 약 4천 건)의 분포가 아니다. 10만·100만 건은 지금 규모가 아니라 늘어났을 때를 가정한 값이다.

## 측정 방법

| 종류 | 방법 |
|---|---|
| SQL | `pg_stat_statements` 로 API 가 실제로 보내는 SQL 을 확인하고, 같은 조건으로 `EXPLAIN (ANALYZE, BUFFERS)`. 준비 1회 뒤 5회의 중앙값·최소·최대. 측정 전 `VACUUM ANALYZE` |
| 부하(닫힌 모델) | 30 VU 가 쉬지 않고 요청. 준비 10초 뒤 30초, 3회. 처리 한계를 볼 때 쓴다 |
| 부하(열린 모델) | 초당 요청 수 고정. 준비 10초 뒤 30초, 3회. 전후 비교에 쓴다 |
| 서버 지표 | `/actuator/prometheus` 를 1초마다 읽어 커넥션 풀 사용·대기, CPU, 힙을 기록 |

## 한계

- k6·앱·DB 가 같은 PC 에서 CPU 를 나눠 쓴다. 절대 수치가 아니라 같은 조건의 전후 비교로만 쓴다.
- 닫힌 모델에서 초당 1,500건을 넘기면 실패 0~0.3% 와 큰 RPS 편차(334~3,005)가 나왔다. 앱 로그에 오류가 없어 부하 발생 쪽 문제로 보지만 원인은 확인하지 못했다. 그래서 전후 비교는 열린 모델 값만 쓴다.
- SQL 은 매개변수 자리에 값을 직접 넣어 쟀다. JDBC 가 같은 문장을 여러 번 실행한 뒤 쓰는 공용 실행 계획과 다를 수 있다.
- 인덱스 없는 100만 건 기준선은 병렬 전체 스캔이다. 코어가 적은 서버에서는 기준선이 더 느릴 수 있다.
- 측정 구간이 30초로 짧다. 장시간 안정성은 TEST 10 에서 따로 본다.
