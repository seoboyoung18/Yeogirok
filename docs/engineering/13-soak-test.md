# 13. 장시간 안정성 (TEST 10)

- 측정일: 2026-11-26 · 환경: `02-test-environment.md` (측정용 앱 1대, 힙 1GB 고정, 발자취 9만 건·팁 9만 건·회원 5,000명)
- 스크립트: `performance-tests/scripts/soak.py`, `performance-tests/k6/soak.js` · 원본: `performance-tests/results/soak-run1.json`
- 결론: 초당 40건을 60분 동안 보냈을 때 실패는 0건이었고, 지연 시간·힙·커넥션은 시간이 지나도 늘지 않았다. 부하가 끝난 뒤 스레드 수도 처음 값으로 돌아왔다. 늘어난 것은 **멱등키(Redis)와 저장한 데이터**뿐이고 둘 다 설계대로다. 코드는 바꾸지 않았다.

## 방법

- k6(도커)로 정해진 속도의 요청을 보냈다(열린 모델). 초당 40건: 방문 분포(서울 화면) 10, 주변 팁 탐색 10, 내 발자취 목록 8, 내 팁 목록 8, 발자취 저장 4.
- 10분짜리 실행을 6번 이어서 돌렸다(구간별 지연 시간을 따로 얻으려고). 구간 사이에 k6 컨테이너가 다시 뜨는 몇 초 동안은 요청이 없다.
- 요청마다 시드 회원 5,000명 중 한 명을 임의로 골랐다. 저장은 넓은 범위에 흩어 써서 "같은 날 500m 안" 제한에 걸리지 않게 했다.
- 10초마다 서버 지표(`/actuator/prometheus`), Redis(`info memory`, `dbsize`), DB(`pg_stat_activity`, DB 크기)를 읽었다(344번, 읽기 실패 0).
- 카카오는 가짜 서버, 파일 저장소는 S3Mock 이다. 끝난 뒤 이번에 저장한 발자취 14,406건을 지웠다(발자취 수 90,772로 복귀 확인).

- **힙:** GC 뒤 남는 양이 처음 20분 동안 87 → 123MB 로 올랐다가 21~26분 사이 한 번 정리된 뒤 78~82MB 에서 움직이지 않았다. 같은 때 힙 밖 메모리(270 → 200MB)와 올라온 클래스 수(30,513 → 30,095)도 같이 줄었다. 그 뒤 35분 동안 늘지 않았으므로 계속 쌓이는 메모리는 보이지 않는다.
- **GC:** 60분 동안 멈춤 569회, 합계 1.27초(한 번에 평균 약 2ms)다. 전체 시간의 0.04%다.
- **스레드:** 부하 중에 34 → 최대 59까지 조금씩 늘었고, 부하가 끝나고 60초 뒤 34로 돌아왔다. 돌아왔으므로 새는 것은 아니다. 어느 스레드 묶음이 늘었는지는 확인하지 않았다.
- **커넥션:** DB 연결 수는 내내 11(풀 10 + 측정용 조회 1)이었다. 풀에서 동시에 쓰인 최댓값은 4, 대기 0, 대기 시간 초과 0이다. 트랜잭션을 연 채 멈춘 연결은 순간 최대 2개였고 끝난 뒤 0이었다.
- **CPU:** 앱 프로세스 평균 1% 수준이었다. 이 부하는 서버 한계와 거리가 멀다(한계는 TEST 01 `04-load-test-report.md`).

## 결과: 늘어난 것

| 항목 | 시작 전 | 60분 뒤 | 늘어난 양 | 이유 |
|---|---|---|---|---|
| Redis 키 수 | 6,820 | 21,226 | +14,406 | 발자취 저장 1건마다 멱등키 1개(보관 24시간) |
| Redis 메모리 | 3.27MB | 7.17MB | +3.9MB | 위 키. 키 하나에 약 0.27KB |
| DB 크기 | 86.2MB | 90.7MB | +4.5MB | 발자취 14,406건(건당 약 0.3KB, 인덱스 포함) |

- Redis 키는 저장한 건수와 정확히 같은 수만큼 늘었다. 멱등키는 24시간 뒤 스스로 지워진다. 이번 측정에서는 24시간을 기다리지 않아 지워지는 것은 확인하지 않았다.
- 예상(측정 아님): 이 속도(초당 저장 4건)가 24시간 이어지면 멱등키는 약 34만 개, 약 94MB 에서 더 늘지 않는다. 0.27KB × 345,600 으로 계산한 값이다.
- 발자취를 지운 뒤에도 DB 크기는 90.7MB 그대로였다. PostgreSQL 은 지운 자리를 바로 돌려주지 않는다(나중에 자동 정리가 다시 쓴다).
