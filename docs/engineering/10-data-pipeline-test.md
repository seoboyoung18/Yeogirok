# 10. 공식 코스 적재 안정성 (TEST 07)

- 측정일: 2026-11-25 · 환경: `02-test-environment.md` + S3Mock
- 스크립트: `performance-tests/scripts/seed_pipeline.py` · 원본: `performance-tests/results/seed-pipeline-run1.json`
- 결론: 반복 실행·두 서버 동시 실행·강제 종료 뒤 재실행에서 중복과 누락은 없었다. 강제 종료 뒤에는 **적재 잠금이 30분 남아 그동안 다시 띄워도 적재가 돌지 않는 문제**와 고아 사진 2장이 남는 것을 확인했다. 코드는 바꾸지 않았다.

## 현재 구현

- 수집·판정·묶음은 서버 밖 스크립트(`backend/tools/tour-course-fetch`)가 하고, 서버는 묶음 파일(JSON + 사진)을 읽어 넣기만 한다. 투어API 는 서버에서 부르지 않는다.
- 서버 시작 뒤 설정이 켜져 있으면 한 번 돈다(`course/seed/CourseSeedJob`). Redis 잠금 `course-seed:lock`(수명 30분)으로 한 번에 하나만 돈다.
- 코스 하나가 한 트랜잭션이다. 사진을 저장소에 올린 뒤 실패하면 그 코스의 사진을 지운다.
- 이미 넣은 코스(방 제목 `tourapi-course:{contentId}:{bundleId}`)는 건너뛴다.

## 방법

- 실제 적재에 쓴 묶음 두 개의 사본을 썼다: 작은 묶음(코스 18개, 사진 파일 68개, 15MB), 큰 묶음(코스 290개, 사진 파일 989개, 227MB). 원본 폴더는 건드리지 않았고 묶음 데이터는 Git 에 올리지 않았다.
- 앱을 적재 설정(`COURSE_SEED_SOURCE=local`)으로 따로 띄우고, 로그의 "넣음·건너뜀·실패"와 DB·저장소의 개수를 대조했다. 투어API·AWS 는 부르지 않았다.
- 강제 종료는 기록이 60개 들어간 시점에 프로세스를 죽였다.

|---|---|---|---|---|---|---|---|---|
| 1 | 빈 상태에서 작은 묶음 | 넣음 18, 건너뜀 0, 실패 0 | 18 / 18 | 18 | 72 | 70 | 70 | 0 |
| 2 | 같은 묶음으로 다시 | 넣음 0, 건너뜀 18, 실패 0 | 18 / 18 | 18 | 72 | 70 | 70 | 0 |

| 4 | 큰 묶음 적재 중 강제 종료 | (끝 로그 없음) | 60 / 60 | 60 | 288 | 269 | 271 | 2 |

- 작은 묶음 적재는 앱 시작부터 24초, 큰 묶음의 남은 230개는 앱 시작부터 58초였다.
- **중복 없음.** 모든 시나리오에서 방 수와 방 제목 가짓수가 같았다. 재실행·동시 실행에서 같은 코스가 두 번 들어가지 않았다.
- **누락 없음.** 강제 종료 뒤 재실행으로 290개가 모두 들어갔다(넣음 230 + 건너뜀 60). 방문 1,353·사진 행 1,257 은 실제 2차 적재 때의 묶음 수치(장소 1,353, 사진 있는 장소 1,257)와 같다.
- **재실행에서 외부 호출이 없다.** 서버는 묶음 파일만 읽으므로 몇 번을 다시 돌려도 투어API 호출은 0 이다. "재처리로 절약한 호출 수"를 따로 세지는 않았다.

## 발견 1: 강제 종료 뒤 30분 동안 적재가 돌지 않는다

- 강제 종료 직후 잠금의 남은 수명이 1,784초였다(30분에서 16초 지난 값).
- 그 상태에서 다시 띄우면 "공식 코스 적재가 이미 돌고 있어 건너뜁니다"만 남기고 끝난다(5번). INFO 로그라 눈에 띄지 않는다.
- 잠금을 지운 뒤 다시 띄우자 이어서 끝났다(6번).
- 정상 종료나 예외에서는 `finally` 가 잠금을 풀어 문제가 없다. 프로세스가 죽은 경우에만 생긴다.
- 영향: 적재는 사람이 설정을 켜고 한 번 돌리는 운영 작업이다. 도중에 서버가 죽으면 30분을 기다리거나 Redis 에서 `course-seed:lock` 을 지워야 한다. 이 절차는 지금 문서(`infra/README`)에 없다.

| 대안 | 장점 | 단점 |
|---|---|---|
| 잠금 수명을 짧게 하고 도는 동안 주기적으로 연장 | 죽으면 금방 풀린다 | 연장 코드가 필요하다 |
| 운영 문서에 "죽었으면 잠금 키 삭제" 절차 추가 | 코드 변경 없음 | 사람이 알아야 한다 |
| 그대로 두기 | - | 30분 대기 |

- 결정(2026-11-26, 사용자): 운영 문서에 절차만 추가한다. 코드는 바꾸지 않는다. `infra/README.md` 9단계 "적재 중에 백엔드가 죽었을 때"에 증상·확인·잠금 삭제·재시작 순서를 넣었다. 운영 서버에서 이 절차를 실행해 보지는 않았다(로컬 5·6번으로만 확인).

## 발견 2: 강제 종료 시점의 사진 2장이 저장소에 남는다

- 저장소에는 있지만 DB(`visit_images`)에는 없는 사진이 2장 생겼다(4번). 처리 중이던 코스가 사진을 올린 뒤 커밋 전에 죽은 것으로 보인다.
- 재실행 뒤에도 그대로 남았다(6번). 재실행은 새 경로로 다시 올린다.
- `record-photo/` 경로를 정리하는 작업은 없어서 저절로 지워지지 않는다. 예외로 실패한 경우는 코드가 지우지만, 프로세스가 죽으면 지울 기회가 없다.
- 영향은 작다(290개 코스 중 2장). 대조 정리(저장소 목록 − DB 경로)를 만들지는 지금 정하지 않았다.

## 실행하지 않은 것

| 항목 | 상태 |
|---|---|
| 잘못된 데이터가 섞인 묶음 | 미실행. 단위 테스트(`seed` 패키지)에만 있다 |
| 내리기(UNPUBLISH)·다시 넣기(RESEED) | 미실행. 단위 테스트에만 있다 |
| 수집 단계(투어API 호출 한도·타임아웃·원본 저장 뒤 재처리) | 미실행. 서버가 아니라 파이썬 스크립트의 일이고 실제 API 를 부르지 않기로 했다 |
| 데이터 규모를 더 키운 적재(918개 전체) | 미실행 |
| 실제 S3 를 원본·대상으로 한 적재 | 미실행. 로컬 폴더와 S3Mock 을 썼다 |
| 초당 처리량 | 따로 재지 않았다. 앱 시작 시간이 섞인 전체 시간만 있다 |

## 한계

- 각 시나리오 1회다.
- 강제 종료 시점(기록 60개)은 하나만 봤다. 다른 시점에서 고아 사진 수는 달라질 수 있다.
- 사진 저장이 한 PC 안의 S3Mock 이라 실제 적재 시간(18개에 약 11초, 290개에 약 2분이라고 기록돼 있다)과 직접 비교할 수 없다.

## 작업 기록

- 사용자가 정한 것: S3 호환 저장소로 진행.
- AI 에이전트(Claude)가 한 것: 스크립트 작성, 실행, 문서 작성. 운영 코드는 바꾸지 않았다.
- 측정 중 바로잡은 것: 첫 실행은 시나리오 사이 초기화 SQL(`TRUNCATE`)이 외래 키에 걸려 측정 전에 멈췄다. `CASCADE` 를 넣어 다시 돌렸다.
