## 기술 선택 이유

- **사용자·작성자 조회는 열 하나짜리 부분 인덱스로 충분했다.** 한 사람의 발자취·팁이 수십 건이라, 정렬·범위 열을 더한 복합 인덱스(B)가 줄이는 시간은 0.1ms 아래였고 크기는 2배였다.
- **좌표만 담은 인덱스는 넓은 화면에서 손해였다.** 서울 화면은 전체의 5~9% 를 읽는다. 인덱스로 찾은 행을 테이블에서 하나씩 다시 읽는 비용이 병렬 전체 스캔보다 컸다(100만 건 119 → 156ms).
- **쿼리가 쓰는 열을 인덱스에 모두 담으니 테이블을 읽지 않게 됐다.** 046 은 좌표·카테고리·사용자·방문 시각만 쓴다.
- **`visited_at` 을 뺀 덮개 인덱스(C)는 날짜 조건이 붙으면 인덱스가 없을 때보다 느렸다**(100만 건 61.8 → 112.5ms). API 가 `from`·`to` 를 받으므로 D 를 골랐다.
- **삭제한 발자취·공개가 아닌 팁은 이 조회들이 읽지 않아** 모두 부분 인덱스로 만들었다.

## 개선 내용

`V6__add_footprint_tip_indexes.sql` 에 인덱스 4개. 엔티티·쿼리·설정은 바꾸지 않았다.

```sql
create index ix_footprints_user_active on footprints (user_id) where deleted_at is null;
create index ix_footprints_geo_cover on footprints (latitude, longitude)
    include (category_codes, user_id, visited_at) where deleted_at is null;
create index ix_ar_tips_public_geo on ar_tips (latitude, longitude) where status = 'PUBLISHED' and deleted_at is null;
create index ix_ar_tips_author_active on ar_tips (author_id) where deleted_at is null;
```

## 검증 한계와 남은 문제

- **전국 보기(046 도 단위)는 개선되지 않았다.** 전체를 세는 쿼리라 인덱스로 줄지 않는다. 100만 건에서 SQL 한 번에 1.2초다. 미리 집계해 두는 방식은 아직 검토하지 않았다.
- **100만 건 서울 화면은 D 에서 75~122ms 로 흔들렸다.** 실행 계획에서 집계 단계가 `work_mem`(4MB)을 넘어 디스크를 쓰는 것을 봤지만, 흔들림의 원인으로 확정하지는 못했다.
- **덮개 인덱스는 `VACUUM` 직후에 가장 유리하다.** 쓰기가 계속 들어오면 테이블을 일부 읽는다. 쓰기와 섞인 상태에서는 재지 않았다.
- **쓰기 비용이 늘었다.** INSERT 1,000행 기준 10만 건에서 2.4배. 100만 건의 INSERT 값은 실행마다 1.8~7.1ms(인덱스 없음)로 흔들려 배수를 정확히 말하기 어렵다.
- 매개변수에 값을 직접 넣어 쟀고, 데이터는 만든 분포다(`02-test-environment.md`).
- 코스 검색(014)·메인 추천(015)은 이 문서 범위 밖이다. 시드가 따로 필요해 아직 재지 않았다.
- 개인 리포지토리에만 반영했다. 팀 리포지토리·운영 DB 에는 적용하지 않았다.
