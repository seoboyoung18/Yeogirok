# 09. 파일 업로드 검증 (TEST 06)

- 측정일: 2026-11-25 · 환경: `02-test-environment.md` + S3 호환 저장소(Adobe S3Mock, 측정용 compose 의 `s3`)
- 스크립트: `performance-tests/scripts/file_upload.py` · 원본: `performance-tests/results/file-upload-run1.json`
- 결론: 크기·형식·소유자·중복 완료 검증이 모두 기대대로 동작했다. 검증 로직은 바꾸지 않았다. 실제 AWS 를 부르지 않고 돌리려고 저장소 주소 설정 하나를 추가했다.

## 현재 구현

1. 발급(API-012): 형식·크기 한도를 확인하고 업로드 세션(Redis)과 임시 경로 `tmp/{uploadId}` 의 Presigned PUT URL 을 준다.
2. 클라이언트가 S3 에 직접 PUT 한다. 파일 바이트는 백엔드를 지나지 않는다.
3. 완료 확인(API-086): 저장소에서 크기와 앞부분 바이트(형식)를 확인하고, 같은 버킷의 확정 경로(`tip-photo/` 등)로 ETag 조건 복사를 한다. 같은 업로드의 완료는 Redis 잠금으로 하나씩만 처리한다.

## 이번에 넣은 것

`backend/src/main/java/com/ssafy/yeogirok/domain/file/FileStorageConfig.java` 에 선택 설정 `yeogirok.file.endpoint` 를 추가했다.

- 값이 있으면 AWS 대신 그 주소의 S3 호환 저장소를 쓴다(경로 방식 주소). 비어 있으면 지금까지와 같이 AWS 를 쓴다.
- 운영·로컬 개발 설정에는 넣지 않았다. 측정용 `.env.perf` 에서만 준다.
- MinIO 를 쓰려 했지만 이미지를 Docker Hub·quay 에서 받을 수 없어(접근 거부) Adobe S3Mock 을 썼다.
- 회귀 테스트: `./gradlew clean test` 2,125개 중 통과 2,115, 건너뜀 10, 실패 0.

## 결과: 시간

크기별 단계 시간(중앙값 ms, 각 5회, 한 PC 안의 S3Mock):

| 크기 | 발급(012) | 저장소에 직접 PUT | 완료 확인(086) |
|---|---|---|---|
| 100KB | 29 | 20 | 73 |
| 1MB | 33 | 14 | 69 |
| 5MB | 18 | 54 | 64 |
| 20MB | 24 | 107 | 93 |

- 백엔드가 쓰는 시간(발급·완료)은 파일 크기와 거의 무관하다. 100KB 와 20MB 의 완료 확인이 73ms 와 93ms 다. 바이트 전송은 클라이언트와 저장소 사이에서만 일어나고, 백엔드는 앞부분만 읽은 뒤 저장소 안에서 복사한다.
- 서로 다른 회원 20명이 1MB 를 동시에 올렸을 때 모두 완료 200, 전체 0.22초였다.

## 하지 않은 비교

"백엔드 서버를 거치는 업로드"와의 비교는 하지 않았다. 이 프로젝트에는 그런 경로가 없었고, 비교하려면 측정만을 위한 가짜 구현을 만들어야 한다. 위 표는 "직접 업로드 구조에서 백엔드 시간이 파일 크기를 따라가지 않는다"는 것까지만 보여 준다.

## 남는 객체

측정 뒤 저장소에 임시 객체 48개, 확정 객체 43개가 있었다.

- 임시 경로(`tmp/`)는 완료 확인 뒤에도 지우지 않는다. 운영에서는 S3 수명 주기 규칙(1일 뒤 삭제)이 지운다. S3Mock 에는 그 규칙이 없어 그대로 남았다.
- 팁에 연결하지 않은 확정본은 `TipPhotoCleanupJob` 이 확정 24시간 뒤 지운다. 24시간을 기다리지 않아 이번에는 확인하지 않았다.

## 한계

- S3Mock 은 실제 S3 가 아니다. 서명·만료·수명 주기·권한이 없다. ETag 조건 복사가 실제 S3 와 같은 방식으로 실패하는지는 여기서 확인하지 않았다.
- 네트워크가 없는 환경이라 PUT 시간은 실제 업로드 시간을 대표하지 않는다.
