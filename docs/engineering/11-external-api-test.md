# 11. 외부 API 장애와 타임아웃 (TEST 08, 카카오 역지오코딩)

- 측정일: 2026-11-25 · 환경: `02-test-environment.md` (앱 1대, 서버 스레드 최대 200, 커넥션 풀 10)
- 스크립트: `performance-tests/scripts/fake_kakao.py`(가짜 카카오), `external_api_failure.py` · 원본: `performance-tests/results/external-api-run1.json`
- 결론: 카카오가 오류를 돌려주거나 느려도 발자취 저장은 한 건도 실패하지 않았다. 다만 카카오가 응답하지 않으면 저장 한 건이 6초씩 서버 스레드를 잡는다. **코드는 바꾸지 않았다.**

## 현재 구현

발자취 저장(API-041)은 좌표로 주소·위치명·법정동 코드를 얻으려고 카카오 로컬 API 를 두 번 부른다(`global/geo/KakaoReverseGeocoder`: 행정구역, 주소).

- 호출은 트랜잭션과 회원 행 잠금 **밖**에서 먼저 한다(`FootprintCreateService.create`).
- 제한 시간: 연결 2초, 응답 3초(`application.yaml` `yeogirok.kakao.local`). 재시도·서킷 브레이커는 없다.
- 호출이 실패하거나 결과가 없으면 주소를 null 로 저장하고 저장은 계속한다.

## 방법

실제 카카오는 부르지 않았다. 앱의 카카오 주소를 PC 안의 가짜 서버(18200)로 바꿔 띄우고, 가짜 서버의 응답 방식을 바꿔 가며 쟀다.

모드마다: 저장 1건 → 서로 다른 회원 50명 동시 저장. 응답하지 않는 모드에서는 300명 동시 저장 중에 다른 회원의 목록 조회(042) 20건을 함께 보냈다.

## 결과

| 가짜 카카오의 응답 | 저장 1건 | 동시 50건 (중앙값 / 최대) | 응답 | 주소가 채워진 행 (51건 중) | 커넥션 풀 사용 최대 |
|---|---|---|---|---|---|
| 정상 | 0.02초 | 0.08 / 0.11초 | 모두 201 | 51 | - |
| 1초 지연 | 2.04초 | 2.07 / 2.10초 | 모두 201 | 51 | 0 |
| 5초 지연 (응답 제한 3초 초과) | 6.07초 | 6.07 / 6.10초 | 모두 201 | 0 | 0 |
| 응답 없음 | 6.05초 | 6.08 / 6.12초 | 모두 201 | 0 | 0 |
| 429 | 0.03초 | 0.08 / 0.12초 | 모두 201 | 0 | - |
| 500 | 0.03초 | 0.09 / 0.11초 | 모두 201 | 0 | - |
| 503 | 0.04초 | 0.07 / 0.10초 | 모두 201 | 0 | - |
| 깨진 JSON | 0.04초 | 0.08 / 0.10초 | 모두 201 | 0 | - |
| 빈 응답 | 0.04초 | 0.06 / 0.09초 | 모두 201 | 0 | - |
| 응답 없이 연결 끊기 | 0.03초 | 0.10 / 0.14초 | 모두 201 | 0 | - |
| 정상으로 되돌린 직후 | 0.05초 | - | 201 | 채워짐 | - |

("-"는 측정 구간이 0.5초보다 짧아 지표를 읽지 못한 칸이다.)

- **저장 실패 0건.** 10가지 응답 모두에서 저장 요청 510건이 전부 201 이었고 HTTP 5xx 는 없었다. 카카오가 실패하면 주소만 비고 발자취는 남는다.
- **오류 응답은 바로 끝난다.** 429·5xx·깨진 응답·연결 끊김은 0.02~0.04초로 정상과 같다.
- **느린 응답이 문제다.** 두 호출이 차례로 나가서, 1초 지연이면 2초, 응답 제한(3초)을 넘으면 3초 x 2 = 6초가 걸린다.
- **기다리는 동안 DB 커넥션은 잡지 않는다.** 응답 없음·지연 모드에서 커넥션 풀 사용이 0 이었다. 외부 호출을 트랜잭션 밖에 둔 설계가 측정으로 확인됐다.
- **정상으로 돌아오면 바로 복구된다.** 되돌린 직후 첫 저장이 0.05초였고 주소가 채워졌다. 재시도나 차단 상태가 없어 복구에 걸리는 시간도 없다.

## 장애 전파: 카카오가 응답하지 않을 때 300건이 몰리면

| 대상 | 결과 |
|---|---|
| 저장 300건 | 모두 201. 중앙값 6.30초, 최대 12.27초 |
| 그동안 다른 회원의 조회 20건 | 모두 200. 중앙값 1.72초, 최대 6.19초 (평소 0.02~0.05초) |
| 커넥션 풀 | 사용 최대 5, 대기 0 |

- 저장 한 건이 서버 스레드를 6초 잡는다. 서버 스레드가 200개라 201번째부터는 앞 요청이 끝나길 기다려 12초가 걸렸다.
- 카카오와 무관한 조회도 스레드를 기다리느라 최대 6초 늦어졌다. 실패는 없었다.
- DB 는 한가했다(풀 사용 5). 병목은 DB 가 아니라 서버 스레드다.

## 대안 (적용하지 않음)

| 대안 | 장점 | 단점 |
|---|---|---|
| 두 호출을 동시에 보내기 | 느릴 때 6초 → 3초 | 스레드를 하나 더 쓴다. 정상일 때 이득은 수십 ms |
| 응답 제한을 3초보다 줄이기 | 스레드를 잡는 시간이 준다 | 카카오가 조금 느릴 때 주소를 못 채운다. 실제 카카오 응답 시간을 재 본 적이 없어 값을 정할 근거가 없다 |
| 서킷 브레이커(연속 실패 시 일정 시간 호출 생략) | 카카오가 죽어 있는 동안 저장이 바로 끝난다 | 라이브러리와 상태 관리가 추가된다. 주소가 비는 구간이 생긴다 |
| 저장을 먼저 끝내고 주소는 나중에 채우기 | 저장이 카카오와 무관해진다 | 응답에 주소가 없다가 나중에 생긴다. 구조와 API 동작이 바뀐다 |
| 그대로 두기 | 변경 없음. 실패 0건, 복구 즉시 | 카카오가 응답하지 않는 동안 저장이 6초, 몰리면 다른 요청도 늦어진다 |

지금은 그대로 두었다. 실패가 없고, 스레드가 고갈되려면 카카오가 응답하지 않는 상태에서 저장이 초당 수십 건씩 들어와야 한다. 실제 카카오의 응답 시간 분포를 모르는 상태에서 값을 바꾸면 근거 없는 변경이 된다.

| 실제 카카오 호출 | 미실행. 키가 없고, 대량 호출을 하지 않기로 했다 |
| 장애가 이어지는 동안의 긴 부하 | 미실행. 한 번에 몰리는 요청만 봤다 |

## 한계

- 가짜 서버가 받은 호출 수는 저장 51건에 94~111회였다(기대 102회). 연결을 끊는 모드에서는 HTTP 클라이언트가 다시 보낸 것으로 보이고, 지연 모드에서는 제한 시간에 끊긴 호출이 집계에서 빠진 것으로 보인다. 원인을 확인하지 않아 이 값은 근거로 쓰지 않았다.
- 서버 스레드 사용량 지표는 이 환경에서 노출되지 않아 읽지 못했다. "스레드 200개를 다 썼다"는 것은 201번째 이후 요청이 12초 걸린 결과로 추정한 것이다.
- 요청을 보내는 쪽과 서버가 같은 PC 다.

## 작업 기록

- 사용자가 정한 것: P1 테스트 진행.
- AI 에이전트(Claude)가 한 것: 가짜 서버와 스크립트 작성, 실행, 문서 작성. 운영 코드는 바꾸지 않았다.
- 측정 중 바로잡은 것: 첫 실행에서 "주소가 채워진 건수"가 정상 모드에서도 0 으로 나왔다. 저장 응답에 주소 필드가 없는데 응답에서 세려 한 스크립트 오류였고, DB 에서 세도록 고쳐 다시 쟀다.
