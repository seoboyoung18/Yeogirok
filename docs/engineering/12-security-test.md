# 12. 인증·인가·입력 검증 (TEST 09)

- 측정일: 2026-11-26 · 환경: `02-test-environment.md` (측정용 앱 1대, 측정 전용 DB·Redis)
- 스크립트: `performance-tests/scripts/security_check.py` · 원본: `performance-tests/results/security-run1.json`(수정 전), `security-after-fix.json`(수정 후)
- 결론: 판정한 84개 중 79개가 기대값과 같았다. 다른 5개 중 1개는 내 기대값이 틀린 것이었고, 4개(원인 3가지)가 실제로 기대와 다른 동작이다. 다른 회원의 발자취·팁을 읽거나 바꾸는 요청은 모두 거부됐고 DB 행은 그대로였다. SQL 로 해석될 수 있는 문자열은 값으로만 처리됐다. 응답에서 내부 정보(스택·SQL·클래스 이름)는 보이지 않았다. **서명이 맞는 토큰의 클레임이 비정상일 때의 처리 3건**이 기대와 달랐다. 셋 다 서버 비밀값으로 서명해야 만들 수 있는 토큰이라 밖에서 바로 쓸 수 있는 문제는 아니다. 사용자 결정으로 개인 리포지토리에서 세 건을 고쳤고, 같은 스크립트로 다시 돌려 세 건 모두 401 A003 이 되는 것을 확인했다(아래 "수정과 전후 확인").

## 방법

- 요청을 한 건씩 보내고 응답 상태 코드·오류 코드를 기대값과 비교했다. 쓰기 요청은 앞뒤로 DB 행을 비교했다.
- 토큰은 측정용 `JWT_SECRET` 으로 직접 만들었다(서버와 같은 HS256). 비밀값·토큰·응답 원문은 결과 파일에 남기지 않았다.
- 5xx 는 기대값과 상관없이 실패로 봤다. 모든 응답 본문에서 내부 정보의 흔적(`exception`, 패키지 이름, SQL 조각, `jdbc` 등)을 정규식으로 찾았다.
- 취약점 스캐너나 대량 요청은 쓰지 않았다. "막아야 할 요청이 막히는지"를 한 번씩 확인한 것이다.

앱은 A002 일 때만 토큰을 갱신한다. 만료·위조·없음이 서로 다른 코드로 나뉘는 것은 확인됐다.

### 발견 1: role 클레임이 없는 토큰이면 500

- 원인: `JwtConfig` 의 역할 검사가 `ALLOWED_ROLES::contains` 이고 `ALLOWED_ROLES` 는 변경 불가 Set 이다. 클레임이 없으면 `contains(null)` 이 `NullPointerException` 을 던진다(서버 로그로 확인).
- 영향: 서명 검증을 통과한 토큰에서만 생긴다. 서버가 발급하는 토큰에는 항상 role 이 있어 정상 사용에서는 나오지 않는다. 다만 500 이라 앱이 "토큰이 잘못됨"으로 처리하지 못한다. 응답도 공통 실패 형식(`success`·`code`·`message`)이 아니라 스프링 기본 오류 형식(`timestamp`·`status`·`error`·`path`)이었다.
- 제안: `value -> value != null && ALLOWED_ROLES.contains(value)`. 한 줄이다.

### 발견 2: exp 클레임이 없는 토큰이 통과한다

- 원인: 만료 판정을 맡긴 스프링 `JwtTimestampValidator` 는 exp 가 없으면 "만료되지 않음"으로 본다. 필수인지 따로 검사하지 않는다.
- 영향: 서버가 발급하는 토큰에는 항상 exp 가 있다. 비밀값이 새지 않는 한 만들 수 없는 토큰이다. 방어를 한 겹 더 두는 문제다.
- 제안: 검증기에 `exp` 필수 검사 추가(`new JwtClaimValidator<Instant>(JwtClaimNames.EXP, Objects::nonNull)`).

### 발견 3: sub 가 숫자가 아니면 A003 이 아니라 A001

- 원인: `ServiceJwtAuthenticationConverter` 가 `OAuth2AuthenticationException` 을 던지는데, `RestAuthenticationEntryPoint` 는 `InvalidBearerTokenException` 일 때만 A002·A003 으로 나눈다. 그 밖은 "토큰 없음"(A001)이 된다.
- 영향: 401 은 맞고 오류 코드만 다르다. 정상 토큰에서는 생기지 않는다.
- 제안: 변환기에서 `InvalidBearerTokenException` 을 던지기.

세 건 모두 로그인 담당(다른 팀원) 코드다.

조회 조건은 타입·허용값 검사에서 먼저 걸리고, 본문은 바인딩 값으로 저장된다. 본문의 스크립트 문자열은 서버가 바꾸지 않고 그대로 돌려준다. 응답이 JSON 이라 서버 쪽 문제는 아니고, 화면에 그릴 때 글자로 다루는 것은 앱의 일이다(React Native `Text` 는 HTML 로 해석하지 않는다).

## 한계

- 각 항목 1회, 대표 경로(발자취·팁·파일) 위주다. 모든 API 를 훑은 것이 아니다.
