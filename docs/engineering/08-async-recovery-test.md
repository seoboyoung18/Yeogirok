# 08. AR 팁 비동기 게시의 종료·복구 (TEST 05)

- 측정일: 2026-11-25 · 환경: `02-test-environment.md` + 앱을 리눅스 컨테이너(`eclipse-temurin:21-jre`)로 실행
- 스크립트: `performance-tests/scripts/async_recovery.py` · 원본: `performance-tests/results/async-recovery-fast.json`, `async-recovery-default.json`
- 결론: 강제 종료로 끊긴 팁은 18회 모두 복구 작업을 거쳐 재시도하면 게시됐다(미복구·유실·중복 0). 정상 종료(SIGTERM)에서도 게시 작업이 끊기는 문제를 새로 찾았고, 종료 순서를 맞춰 고쳤다(끊긴 팁 142~272건 → 0건).

## 현재 구현

1. 팁 등록(API-049): 팁을 `REGISTERING` 으로 저장하고 Redis 에 작업 상태를 남긴 뒤 202 를 준다(`tip/service/TipCreateService`).
2. 커밋 뒤 `TipPublisher`(@Async, 스프링 기본 실행기)가 사진을 연결하고 `PUBLISHED` 로 바꾼다. 작업은 메모리에만 있다.
3. `StuckTipRecoveryJob`: 5분마다, `REGISTERING` 인 채 5분이 지난 팁을 `FAILED`(재시도 가능)로 바꾼다. **다시 게시하지는 않는다.**
4. 사용자가 재시도 API(051)를 부르면 다시 게시한다.
5. 종료 설정: `spring.task.execution.shutdown.await-termination: true`, 기간 30초.

## 방법

- 앱을 컨테이너로 띄워 종료 신호를 구분했다: `docker kill`(SIGKILL), `docker stop -t 40`·`-t 10`(SIGTERM 뒤 그 시간만큼 기다림. 10초는 도커 기본값이자 지금 서버 compose 의 값).
- 한 번의 실행: 팁 등록 N건을 한꺼번에 보내고 첫 202 가 오자마자 앱을 끈다 → DB 상태를 센다 → 앱을 다시 띄운다 → `REGISTERING` 이 없어질 때까지 기다린다 → `FAILED` 팁을 051 로 재시도 → `PUBLISHED` 확인.
- 반복 측정은 복구 주기·기준을 20초로 줄인 설정(`--fast`)으로 했다. 운영 값(5분·5분)으로는 1회 쟀다.
- 게시 작업 자체는 몇 ms 다. 10건으로는 강제 종료해도 끊긴 팁이 0건이어서 50~500건으로 쟀다.

## 결과 1: 강제 종료 (SIGKILL, 복구 주기 20초 설정)

"저장된 팁"은 종료 시점에 DB 에 커밋된 수다(요청 중 일부는 응답 전에 서버가 죽어 저장되지 않았다).

| 요청 수 | 저장된 팁 (3회) | 끊긴 팁 `REGISTERING` (3회) | 복구 안 된 팁 | 재시도(051) 응답 | 재시도 뒤 `PUBLISHED` |
|---|---|---|---|---|---|
| 50 | 50 / 50 / 50 | 7 / 32 / 15 | 0 / 0 / 0 | 모두 202 | 50 / 50 / 50 |
| 200 | 80 / 128 / 113 | 78 / 125 / 107 | 0 / 0 / 0 | 모두 202 | 80 / 128 / 113 |
| 500 | 149 / 115 / 90 | 143 / 114 / 87 | 0 / 0 / 0 | 모두 202 | 149 / 115 / 90 |
| 500, 복구 전에 한 번 더 강제 종료 | 289 | 267 | 0 | 모두 202 | 289 |
| 500, 복구 전에 Redis 재시작(키 유실) | 273 | 255 | 0 | 모두 202 | 273 |

- 자동 복구 성공률(끊긴 팁이 재시도 가능한 `FAILED` 로 바뀐 비율): 11회 합계 1,230건 중 1,230건.
- 재시도 뒤 전체 행 수가 종료 직후와 같았다(유실·중복 0).
- 복구까지 걸린 시간은 앱이 다시 뜬 뒤 21.3~23.7초(20초 설정이라 그렇다).
- 응답을 받지 못한 요청(50건에서 0, 500건에서 221~417)은 대부분 저장도 되지 않았다. 클라이언트가 같은 멱등키로 다시 보내야 한다.

## 결과 2: 운영 값 (5분 주기 · 5분 기준, 1회)

| 항목 | 값 |
|---|---|
| 요청 200건 강제 종료 직후 | `PUBLISHED` 3, `REGISTERING` 197 |
| 복구까지(끊긴 때부터) | 334.0초 |
| 복구까지(앱이 다시 뜬 때부터) | 302.9초 |
| 복구 안 된 팁 | 0 |

- 복구 작업의 첫 실행이 시작 5분 뒤라, 앱이 다시 뜬 뒤 약 5분에 한 번에 정리됐다.
- "5분 안에 복구"라고 말할 수 없다. 이번은 5분 34초였다. 팁이 끊긴 지 5분이 지나야 대상이 되고 작업은 5분마다 돌기 때문에, 시점이 어긋나면 최대 10분 가까이 걸릴 수 있다(코드로 계산한 값, 재현하지 않음). 서버가 내려가 있던 시간은 여기에 더해진다.

## 결과 3: 정상 종료 (SIGTERM) — 문제 발견

요청 500건, 각 3회. 앱은 기다리지 않고 1.2~1.4초 만에 끝났다(종료 코드 143).

| 종료 방식 | 저장된 팁 | 종료 직후 `PUBLISHED` | 종료 직후 `REGISTERING` | 종료 직후 `FAILED` | 재시도 뒤 `PUBLISHED` |
|---|---|---|---|---|---|
| SIGTERM, 40초 대기 | 314 / 400 / 500 | 50 / 81 / 131 | 160 / 229 / 272 | 104 / 90 / 97 | 314 / 400 / 500 |
| SIGTERM, 10초 대기 | 388 / 316 / 396 | 92 / 64 / 69 | 190 / 142 / 238 | 106 / 110 / 89 | 388 / 316 / 396 |

- 정상 종료인데 저장된 팁의 67~84% 가 게시되지 못했다. 대기 시간(10초·40초)은 결과에 차이를 주지 않았다.
- 원인(진단 실행의 컨테이너 로그, 게시 실패 330건):
  - `Commencing graceful shutdown` → 0.3초 뒤 `Graceful shutdown complete`. 웹 서버는 바로 닫힌다.
  - 곧바로 Redis 연결과 DB 연결이 닫힌다. 그 뒤에도 비동기 실행기는 대기 중이던 게시 작업을 계속 실행한다.
  - 작업이 `IllegalStateException: LettuceConnectionFactory is STOPPING / has been STOPPED`(Redis), `CannotCreateTransactionException: Could not open JPA EntityManager`(DB, 257건)로 실패한다.
  - Redis 만 닫힌 시점에 실패한 작업은 팁을 `FAILED` 로 바꾸고, DB 까지 닫힌 뒤 실패한 작업은 아무것도 못 바꿔 `REGISTERING` 으로 남는다.
- 즉 "종료 대기 30초"는 작업이 끝나기를 기다리지만, 작업이 쓸 Redis·DB 가 먼저 닫혀 목적을 이루지 못한다. Phase 1 에서 예상한 "컨테이너 종료 유예 10초가 30초보다 짧다"는 원인이 아니었다.
- 유실은 없다. 끊긴 팁은 복구 작업과 재시도를 거쳐 모두 게시됐다. 다만 배포(정상 종료)마다 그 순간의 등록이 실패로 보이고, 사용자가 재시도해야 한다.
- 조건: 500건을 한꺼번에 보낸 상황이다. 요청이 적은 평소 배포에서는 끊길 틈이 훨씬 좁다(10건 시험에서 0건).

## 정상 종료 문제 개선: 종료 순서 맞추기 (적용함)

`backend/src/main/java/com/ssafy/yeogirok/global/config/AsyncTaskDrain.java` 를 새로 넣었다. 기존 코드와 설정은 바꾸지 않았다.

- 원인을 스프링 클래스에서 확인했다. 종료 대기(`await-termination`)가 켜져 있으면 기본 실행기는 종료 단계에서 아무것도 하지 않고 빈을 없앨 때에야 남은 작업을 기다린다(`ExecutorConfigurationSupport`). Redis 연결(`LettuceConnectionFactory`, 단계 0)은 그 전에 멈춘다.
- `AsyncTaskDrain` 은 종료 단계 중 "웹 서버가 닫힌 뒤, Redis 연결이 멈추기 전"에 끼어들어 기본 실행기를 닫고(새 작업은 받지 않음) 실행 중·대기 중인 작업이 끝날 때까지 기다린다. 기다리는 시간은 기존 설정(`await-termination-period: 30s`)이다.
- 기간을 넘기면 경고 로그만 남긴다. 그때 끊긴 팁은 전과 같이 복구 작업이 정리한다.

같은 스크립트로 다시 쟀다(요청 500건, 각 3회, 복구 주기 20초 설정). 원본: `results/async-recovery-fast.json`(전), `async-recovery-fast-after-drain.json`(후).

| 지표 | 수정 전 | 수정 후 | 측정 조건 |
|---|---|---|---|
| SIGTERM·40초 대기: 종료 직후 `REGISTERING` | 160 / 229 / 272 | 0 / 0 / 0 | 저장된 팁 전 314·400·500, 후 349·385·331 |
| SIGTERM·40초 대기: 종료 직후 `FAILED` | 104 / 90 / 97 | 0 / 0 / 0 | 같은 실행 |
| SIGTERM·40초 대기: 종료 직후 `PUBLISHED` | 50 / 81 / 131 | 349 / 385 / 331 (저장된 팁 전부) | 같은 실행 |
| SIGTERM·10초 대기: 종료 직후 `REGISTERING` | 190 / 142 / 238 | 0 / 0 / 0 | 저장된 팁 전 388·316·396, 후 352·382·372 |
| SIGTERM·10초 대기: 종료 직후 `FAILED` | 106 / 110 / 89 | 0 / 0 / 0 | 같은 실행 |
| 종료에 걸린 시간 | 1.2~1.4초 | 1.6~2.0초 | `docker stop` 이 돌아올 때까지 |
| 강제 종료(SIGKILL) 200건 | (전과 같은 동작) | 끊김 184 → 복구·재시도 뒤 200건 게시 | 1회. 강제 종료는 이 수정과 무관하다 |

- 정상 종료 6회 모두 저장된 팁이 전부 게시된 채로 끝났다. 재시도가 필요한 팁이 없었다.
- 종료가 0.4~0.6초 길어졌다. 대기 작업을 끝내는 시간이다. 도커 기본 종료 유예(10초) 안이라 서버 compose 는 바꾸지 않았다.
- 응답을 받지 못한 요청(115~169건)은 그대로다. 종료 신호 뒤 웹 서버가 받지 않은 요청이고 저장도 되지 않았다. 클라이언트가 같은 멱등키로 다시 보내야 한다.
- 회귀 테스트: 단위 테스트 `AsyncTaskDrainTest` 3개(대기 작업을 끝냄, 기간이 지나면 돌아옴, 단계 값이 웹 서버보다 작고 Redis 연결보다 큼). 전체 `./gradlew clean test` 2,125개 중 통과 2,115, 건너뜀 10, 실패 0.
- 한계: 대기 작업이 30초 넘게 걸리는 경우(작업이 매우 많거나 느린 경우)는 재지 않았다. 도커 종료 유예가 10초라, 그런 경우에는 10초에 강제 종료된다. 단계 값은 스프링 부트의 웹 서버 종료 단계와 Redis 연결 단계에 기대므로 버전을 올리면 단위 테스트로 다시 확인해야 한다.

## 해결 대안 (검토 기록)

| 대안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| 종료 순서 맞추기 (선택) | 웹 서버가 닫힌 뒤, Redis·DB 가 닫히기 전에 비동기 실행기의 대기 작업을 끝낸다(종료 단계에 끼워 넣는 컴포넌트) | 원인을 직접 고친다. 측정으로 전후를 확인할 수 있다 | 스프링 종료 순서를 다루는 코드라 버전이 바뀌면 다시 확인해야 한다 |
| 복구 작업이 직접 다시 게시 | `FAILED` 로 돌리지 않고 게시를 다시 시도 | 사용자 재시도가 필요 없다 | 지금 설계(사용자 재시도)와 다르다. 반복 실패 처리 필요 |
| 작업을 메모리 대신 DB·Redis 큐에 저장 | 종료·재시작과 무관하게 이어서 처리 | 가장 튼튼하다 | 구조 변경이 크다 |
| 그대로 두기 | 복구 작업과 재시도에 맡긴다 | 변경 없음 | 배포 때마다 일부 등록이 실패로 보인다 |

## 주장할 수 있는 것과 없는 것

- 할 수 있음: 서버가 강제 종료돼도 접수된 팁은 사라지지 않고, 복구 작업을 거쳐 재시도하면 게시된다(18회, 미복구 0, 유실·중복 0).
- 할 수 있음(수정 후): 정상 종료에서는 대기 중이던 게시 작업을 끝내고 내려간다(500건 x 6회, 끊긴 팁 0).
- 할 수 없음: "자동으로 다시 게시된다"(재시도 API 를 불러야 한다), "5분 안에 복구된다"(측정 5분 34초, 최대 약 10분).
