# 06. 발자취 저장 동시성 (TEST 03)

- 측정일: 2026-11-25 · 환경: `02-test-environment.md` (V6 인덱스 적용, 발자취 10만 건)
- 스크립트: `performance-tests/scripts/concurrency_footprint.py` · 원본: `performance-tests/results/concurrency-*.json`
- 결론: 현재 구현(회원 행 `FOR UPDATE`)은 모든 시나리오에서 정합성 위반 0건이었다. 코드를 바꾸지 않았다.

## 확인하려는 규칙

API-041 은 같은 날(04:00 기준) 내가 남긴 발자취와 500m 이내면 거부한다(409 F003). "조회 → 거리 확인 → 저장"이 한 사용자 안에서 겹치면 둘 다 "없음"을 보고 둘 다 저장할 수 있다.

현재 구현(`footprint/service/FootprintCreateService.save`):

1. 역지오코딩(외부 호출)은 트랜잭션 밖에서 먼저 한다.
2. 트랜잭션 안에서 `UserLock.lock(userId)` — `users` 행을 `SELECT ... FOR UPDATE` 로 잠근다.
3. 잠금을 잡은 뒤 오늘 발자취를 읽고(READ COMMITTED 라 먼저 커밋된 것이 보인다) 거리를 확인한 뒤 저장한다.
4. 커밋하면 잠금이 풀린다. 삭제(API-045)와 탈퇴도 같은 잠금을 쓴다.

## 방법

- 측정용 앱(실제 PostgreSQL·Redis)에 HTTP 요청을 한꺼번에 보낸다. 스레드가 모두 준비된 뒤 동시에 출발한다(Barrier).
- 요청마다 멱등키가 다르다. 멱등 처리가 아니라 사용자 잠금만 본다.
- 응답 코드와, 끝난 뒤 DB 에 남은 삭제되지 않은 행 수를 대조한다. 시나리오마다 3회.
- 서버 안에서 실제로 겹치는 정도는 커넥션 풀(10)과 서버 스레드(200)에 막힌다. "500건 동시"는 500건이 한꺼번에 도착했다는 뜻이다.
- 대조군: `FootprintCreateService` 의 `userLock.lock(userId);` 한 줄만 지운 **비교용 빌드**를 임시 폴더에서 만들어 같은 DB 에 띄웠다. 과거에 운영하던 구조가 아니라 이 측정을 위해 만든 것이고 저장소에는 없다.

## 결과 1: 같은 사용자 · 같은 위치 (기대: 1건 저장, 나머지 409 F003)

| 요청 수 | 잠금 있음 · 앱 1대 (3회) | 잠금 있음 · 앱 2대 (3회) | 잠금 없음 · 비교용 (3회) |
|---|---|---|---|
| 5 | 저장 1 / 1 / 1 | 1 / 1 / 1 | **5 / 4 / 4** |
| 10 | 1 / 1 / 1 | 1 / 1 / 1 | **8 / 8 / 7** |
| 50 | 1 / 1 / 1 | 1 / 1 / 1 | **5 / 4 / 5** |
| 100 | 1 / 1 / 1 | 1 / 1 / 1 | **4 / 4 / 6** |
| 200 | 1 / 1 / 1 | 1 / 1 / 1 | **5 / 4 / 5** |
| 500 | 1 / 1 / 1 | 1 / 1 / 1 | **10 / 7 / 8** |

- 잠금이 있으면 18회 모두 1건만 저장됐고 나머지는 모두 409 F003 이었다. 앱 2대로 요청을 나눠 보내도 같았다(잠금이 DB 에 있다).
- 잠금을 빼면 18회 모두 규칙이 깨졌다(4~10건 저장).
- 세 구성 모두 HTTP 5xx 0건, 연결 실패 0건, 데드락 0건(`pg_stat_database.deadlocks`), 앱 로그 ERROR 0건.

## 결과 2: 그 밖의 시나리오 (각 3회)

| 시나리오 | 기대 | 잠금 있음 · 1대 | 잠금 있음 · 2대 | 잠금 없음 · 비교용 |
|---|---|---|---|---|
| 같은 사용자 · 10m 간격 50건 (모두 500m 안) | 저장 1 | 1 / 1 / 1 | 1 / 1 / 1 | **2 / 3 / 2** |
| 같은 사용자 · 600m 간격 50건 (모두 500m 밖) | 저장 50 | 50 / 50 / 50 | 50 / 50 / 50 | 50 / 50 / 50 |
| 서로 다른 사용자 50명 · 같은 위치 | 저장 50 | 50 / 50 / 50 | 50 / 50 / 50 | 50 / 50 / 50 |
| 발자취 1건 있는 상태에서 삭제 1건 + 근처 저장 20건 | 남은 것 1 이하 | 1 / 1 / 1 | 1 / 1 / 1 | **0 / 6 / 5** |

- 잠금이 사용자 단위라 서로 다른 사용자는 서로 막지 않는다(50명 모두 저장).
- 삭제와 저장이 겹쳐도 남은 발자취는 1건이었다(삭제가 먼저면 저장 1건 성공, 저장이 먼저면 모두 거부 뒤 삭제 → 그 뒤 저장 성공).

|---|---|---|---|
| 5 | 25 / 15 / 33 | 26 / 17 / 34 | 28 / 19 / 36 |
| 10 | 24 / 21 / 19 | 28 / 26 / 25 | 30 / 28 / 25 |
| 50 | 58 / 60 / 59 | 85 / 88 / 89 | 87 / 93 / 92 |

한 사용자의 요청은 한 줄로 처리되므로 시간이 요청 수에 비례한다(1건당 약 2ms). 500건에서도 타임아웃은 없었다(HikariCP 연결 대기 제한 기본 30초 안).

## 발견: 한 사용자의 요청 몰림이 다른 사용자를 늦춘다

같은 사용자의 저장 200건이 몰리는 동안 다른 회원의 목록 조회(042) 20건을 함께 보냈다.

| 조건 | 다른 회원 조회 P50 ms (3회) | P95 ms (3회) |
|---|---|---|
| 조회 20건만 | 30 / 17 / 19 | 49 / 27 / 28 |
| 같은 사용자 저장 200건과 함께 | 321 / 289 / 168 | 350 / 391 / 442 |

- 원인: 저장 요청마다 커넥션을 하나 잡은 채 같은 회원 행 잠금을 기다린다. 풀 10개가 한 사용자의 대기로 차고, 다른 사용자의 요청은 커넥션을 기다린다.
- 정합성 문제는 아니다. 조회는 모두 200 이었고 늦어졌을 뿐이다.
- 한 사용자가 200건을 동시에 보내는 것은 정상 사용이 아니라 오작동·악용에 가깝다. 지금은 고치지 않았다. 대안은 아래와 같고 모두 측정하지 않았다.

| 대안 | 장점 | 단점 |
|---|---|---|
| 사용자별 요청 수 제한(게이트웨이·필터) | 원인을 입구에서 막는다 | 새 구성 요소·정책 필요 |
| 잠금 대기 제한(`lock_timeout`, `NOWAIT`) | 커넥션 점유 시간을 줄인다 | 정상적인 짧은 대기도 실패할 수 있고 새 오류 응답이 필요 |
| 커넥션을 잡기 전에 앱 안에서 사용자별로 줄 세우기 | 풀을 지킨다 | 앱이 여러 대면 효과가 줄고 코드가 복잡해진다 |

## 잠금 방식 비교

| 방식 | 평가 |
|---|---|
| 잠금 없음 | 이번 측정에서 규칙이 매번 깨졌다 |
| PostgreSQL advisory lock (`pg_advisory_xact_lock(userId)`) | 초기 구현. 회원 테이블이 생긴 뒤 `FOR UPDATE` 로 바꿨다(코드 이력). 탈퇴와 같은 행을 잠그게 되어 "탈퇴한 회원의 저장"을 같은 잠금으로 막는다. 이번에 따로 측정하지 않았다 |
| 회원 행 `FOR UPDATE` (현재) | 5~500건·앱 2대에서 위반 0건. 잠금이 DB 에 있어 앱 대수와 무관하다 |
| Redis 분산 락 | 필요성을 찾지 못해 측정하지 않았다. DB 트랜잭션과 따로 풀리므로 수명 관리가 더 필요하다 |

## 한계

- 요청을 보내는 쪽과 서버가 같은 PC 다. 응답 시간은 참고값이다.
- 역지오코딩 키가 없어 외부 호출 시간이 0 이다. 실제로는 저장 전에 외부 호출(제한 3초)이 있어 요청이 흩어진다.
- "앱 2대"는 같은 PC 에서 포트만 다른 두 프로세스다. 네트워크 지연이 있는 실제 다중 서버는 아니다.
- 비교용 빌드는 저장소에 없다. 다시 만들려면 임시 worktree 에서 `FootprintCreateService` 의 `userLock.lock(userId);` 줄을 지우고 `bootJar` 한 뒤 다른 포트로 띄운다.
