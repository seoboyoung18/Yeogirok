# 07. Redis 멱등키 처리와 장애 상황 (TEST 04)

- 측정일: 2026-11-25 · 환경: `02-test-environment.md` (앱 1대, V6 적용)
- 스크립트: `performance-tests/scripts/idempotency_failures.py` · 원본: `performance-tests/results/idempotency-app1.json`
- 결론: 정상 흐름은 설계대로 동작했다. 장애 상황에서 문제 3개를 재현했다. **이 문서 시점에는 코드를 고치지 않았다.**

## 현재 구현

`global/idempotency/IdempotencyService.execute` (컨트롤러 12개, 28곳):

1. Redis 에 처리 중 표시를 `SET NX` 로 건다(수명 30초). 건 요청만 실제 처리를 한다.
2. 처리가 끝나면(트랜잭션 커밋 뒤) 값을 `{요청 해시, 결과 ID}` 로 바꾸고 24시간 둔다. Lua 로 "내 표시가 그대로거나 사라졌을 때만" 저장한다.
3. 처리가 실패하면 표시를 지운다.
4. 표시를 못 건 요청: 요청 내용이 다르면 C005, 처리 중이면 C018, 끝났으면 결과 ID 로 다시 조회해 돌려준다.

Redis 와 DB 는 한 트랜잭션이 아니다. 코드 주석도 "Redis 키만으로 DB 중복 반영을 막았다고 보지 않는다"고 적고 있다.

## 결과 2: 장애 상황

### 문제 A. 완료 기록이 없으면 처리가 다시 실행된다 — 팁이 2건 생겼다

완료 기록을 지운 뒤(= Redis 가 재시작해 키를 잃었거나, 완료 기록 저장에 실패했거나, 보관 기간이 지난 상태) 같은 키로 다시 보냈다.

| API | 처음 | 같은 키로 다시 | DB |
|---|---|---|---|
| 발자취 저장(041) | 201 | **409 F003** (처음 결과가 아님) | 1행 |
| 팁 등록(049, 사진 없음) | 202, tipId 100001 | **202, tipId 100002** | **2행** |

- 발자취는 "같은 날 500m" 규칙이 우연히 중복을 막았다. 그래도 응답은 처음과 다르다(성공했던 요청이 재전송에서 409).
- 팁 등록은 DB 에 막는 장치가 없어 **같은 멱등키로 팁이 2건** 생겼다.
- 나머지 26곳은 확인하지 않았다. DB 유일 제약이나 version 검사가 있는 곳은 막히고, 없는 곳은 팁처럼 중복될 수 있다.

### 문제 B. 처리가 30초(처리 중 표시 수명)를 넘으면 두 번째 요청도 실행된다

회원 행 잠금을 밖에서 36초 잡아 요청을 트랜잭션 안에 세워 두었다.

| 시점 | 요청 | 결과 |
|---|---|---|
| 0초 | 처음 요청 | 35.1초 뒤 201 |
| 10초 | 같은 키 | 409 C018 (정상) |
| 32초 | 같은 키 | 표시가 사라져 **처리에 들어감** → 3.1초 뒤 409 F003 |
| 끝난 뒤 | 같은 키 | **409 F003**. Redis 에 이 키의 기록이 없음 |

- 처음 요청의 완료 기록은 저장되지 않았다(다른 요청이 표시를 다시 걸어 Lua 가 저장을 건너뜀). 두 번째는 실패해 표시를 지웠다. 그래서 성공한 요청인데도 기록이 남지 않았다.
- DB 는 1행이다(발자취 규칙이 막음). 막는 장치가 없는 API 였다면 두 번 실행됐다.
- 정상 처리는 수십 ms 라 30초를 넘기려면 DB 잠금 대기나 외부 호출 지연이 겹쳐야 한다.

### 문제 C. Redis 가 멈추면 모든 요청이 60~120초 매달린다

요청이 트랜잭션 안에서 기다리는 동안 측정용 Redis 컨테이너를 멈췄다(`docker stop`).

| 요청 | 결과 |
|---|---|
| 진행 중이던 발자취 저장 | DB 에는 저장됨(1행). 완료 기록 저장이 **60초 뒤 시간 초과**(로그 `멱등키 결과 저장에 실패했습니다`). 클라이언트(제한 60초)는 응답을 받지 못함 |
| Redis 중단 중 새 조회(042) | **60.0초 뒤 200** |
| Redis 중단 중 새 저장(041) | **120.0초 뒤 500 C014** |
| Redis 가 다시 뜬 뒤 처음 요청과 같은 키 | 409 F003 (문제 A 와 같은 상태) |
| Redis 가 다시 뜬 뒤 새 요청 | 6.1초 안에 201 (따로 조치 없이 복구) |

- 원인: Redis 명령 제한 시간을 설정하지 않아 Lettuce 기본값 60초다(`RedisCommandTimeoutException: Command timed out after 1 minute(s)`).
- 조회도 60초 걸린 이유: 인증 단계에서 탈퇴 회원 확인(`WithdrawnUserTokens`)이 Redis 를 읽는다. 시간 초과 뒤에는 통과시켜 200 이 나왔다.
- 저장은 인증 60초 + 처리 중 표시 60초 = 120초 뒤 실패했다.
- Redis 가 잠깐만 멈춰도 서버 스레드(최대 200)가 60초씩 묶인다. 스레드가 다 묶인 상태는 이번에 재지 않았다.

## 해결 대안 (적용 전, 결정 필요)

| 문제 | 대안 | 장점 | 단점 | 변경 범위 |
|---|---|---|---|---|
| C | Redis 명령·연결 제한 시간 설정(`spring.data.redis.timeout`, `connect-timeout`) | 설정 두 줄. 매달리는 시간이 60초 → 설정값 | Redis 가 느릴 때 정상 요청도 실패할 수 있어 값 선택이 필요 | 설정(전 기능 공통, 팀원 코드에도 영향) |
| A·B | 중복되면 안 되는 테이블에 "요청 키" 열과 유일 제약(예: `ar_tips (author_id, request_key)`) | Redis 와 무관하게 DB 가 막는다. 기간 제한 없음 | API 마다 열·마이그레이션·중복 시 기존 행 반환 처리가 필요 | 엔티티·마이그레이션·서비스 (API 별) |
| A·B | 멱등 기록을 DB 테이블에 두고 처리와 같은 트랜잭션으로 저장 | 한 곳에서 28곳 모두 해결 | 공통 구조를 바꿔야 하고 트랜잭션 경계를 28곳에서 맞춰야 함 | 공통 모듈 + 호출부 전체 |
| B | 처리 중 표시 수명을 늘리거나 처리 중에 연장 | 설정 변경만으로 가능 | 서버가 죽었을 때 재시도 가능해지는 시간도 같이 늘어남 | 설정 또는 공통 모듈 |
| A | 운영 Redis 영속화(appendonly)는 이미 켜져 있다(`infra/docker-compose.yml`) | 재시작으로 인한 키 유실은 줄어든다 | 완료 기록 저장 실패·30초 초과는 그대로 | 없음 |

## 주장할 수 있는 것과 없는 것

- 할 수 있음: Redis 가 정상일 때 같은 키의 반복·동시 요청은 한 번만 처리되고 같은 결과를 돌려준다(24시간).
- 할 수 없음: "정확히 한 번 처리", "영구적인 중복 방지". 완료 기록이 없거나 처리가 30초를 넘으면 다시 실행된다.

## 측정 중 알게 된 것

- 측정용 앱이 예약 작업으로 **실제 S3(개발 버킷)를 한 번 호출했다**(`S3 요청에 실패했습니다: AccessDeniedException`, 14:36). `local` 프로필의 기본 버킷 이름과 이 PC 의 AWS 기본 자격 증명으로 나간 호출이고 권한 거부로 끝나 바뀐 것은 없다. 측정 환경은 외부를 호출하지 않아야 하므로 `.env.perf` 에서 버킷 이름을 비우도록 README 를 고쳤다.
- 측정용 Redis 는 디스크에 쓰지 않는다. 운영 Redis 는 appendonly 가 켜져 있어 재시작 때 키가 남는다. 이 차이 때문에 "재시작으로 키 유실"은 운영에서 덜 일어난다.
