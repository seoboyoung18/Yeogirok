# 07. Redis 멱등키 처리와 장애 상황 (TEST 04)

- 측정일: 2026-11-25 · 환경: `02-test-environment.md` (앱 1대, V6 적용)
- 스크립트: `performance-tests/scripts/idempotency_failures.py` · 원본: `performance-tests/results/idempotency-app1.json`
- 결론: 정상 흐름은 설계대로 동작했다. 장애 상황에서 문제 3개를 재현했다. 문제 C(Redis 중단 시 60~120초 매달림)는 설정으로, 문제 A 는 팁 등록 한 곳만 DB 유일 제약으로 고쳤다. 문제 B 와 나머지 26곳은 그대로다.

## 현재 구현

`global/idempotency/IdempotencyService.execute` (컨트롤러 12개, 28곳):

1. Redis 에 처리 중 표시를 `SET NX` 로 건다(수명 30초). 건 요청만 실제 처리를 한다.
2. 처리가 끝나면(트랜잭션 커밋 뒤) 값을 `{요청 해시, 결과 ID}` 로 바꾸고 24시간 둔다. Lua 로 "내 표시가 그대로거나 사라졌을 때만" 저장한다.
3. 처리가 실패하면 표시를 지운다.
4. 표시를 못 건 요청: 요청 내용이 다르면 C005, 처리 중이면 C018, 끝났으면 결과 ID 로 다시 조회해 돌려준다.

Redis 와 DB 는 한 트랜잭션이 아니다. 코드 주석도 "Redis 키만으로 DB 중복 반영을 막았다고 보지 않는다"고 적고 있다.

## 결과 2: 장애 상황

### 문제 A. 완료 기록이 없으면 처리가 다시 실행된다 — 팁이 2건 생겼다

완료 기록을 지운 뒤(= Redis 가 재시작해 키를 잃었거나, 완료 기록 저장에 실패했거나, 보관 기간이 지난 상태) 같은 키로 다시 보냈다.

| API | 처음 | 같은 키로 다시 | DB |
|---|---|---|---|
| 발자취 저장(041) | 201 | **409 F003** (처음 결과가 아님) | 1행 |
| 팁 등록(049, 사진 없음) | 202, tipId 100001 | **202, tipId 100002** | **2행** |

- 발자취는 "같은 날 500m" 규칙이 우연히 중복을 막았다. 그래도 응답은 처음과 다르다(성공했던 요청이 재전송에서 409).
- 팁 등록은 DB 에 막는 장치가 없어 **같은 멱등키로 팁이 2건** 생겼다.
- 나머지 26곳은 확인하지 않았다. DB 유일 제약이나 version 검사가 있는 곳은 막히고, 없는 곳은 팁처럼 중복될 수 있다.

### 문제 B. 처리가 30초(처리 중 표시 수명)를 넘으면 두 번째 요청도 실행된다

회원 행 잠금을 밖에서 36초 잡아 요청을 트랜잭션 안에 세워 두었다.

| 시점 | 요청 | 결과 |
|---|---|---|
| 0초 | 처음 요청 | 35.1초 뒤 201 |
| 10초 | 같은 키 | 409 C018 (정상) |
| 32초 | 같은 키 | 표시가 사라져 **처리에 들어감** → 3.1초 뒤 409 F003 |
| 끝난 뒤 | 같은 키 | **409 F003**. Redis 에 이 키의 기록이 없음 |

- 처음 요청의 완료 기록은 저장되지 않았다(다른 요청이 표시를 다시 걸어 Lua 가 저장을 건너뜀). 두 번째는 실패해 표시를 지웠다. 그래서 성공한 요청인데도 기록이 남지 않았다.
- DB 는 1행이다(발자취 규칙이 막음). 막는 장치가 없는 API 였다면 두 번 실행됐다.
- 정상 처리는 수십 ms 라 30초를 넘기려면 DB 잠금 대기나 외부 호출 지연이 겹쳐야 한다.

### 문제 C. Redis 가 멈추면 모든 요청이 60~120초 매달린다

요청이 트랜잭션 안에서 기다리는 동안 측정용 Redis 컨테이너를 멈췄다(`docker stop`).

| 요청 | 결과 |
|---|---|
| 진행 중이던 발자취 저장 | DB 에는 저장됨(1행). 완료 기록 저장이 **60초 뒤 시간 초과**(로그 `멱등키 결과 저장에 실패했습니다`). 클라이언트(제한 60초)는 응답을 받지 못함 |
| Redis 중단 중 새 조회(042) | **60.0초 뒤 200** |
| Redis 중단 중 새 저장(041) | **120.0초 뒤 500 C014** |
| Redis 가 다시 뜬 뒤 처음 요청과 같은 키 | 409 F003 (문제 A 와 같은 상태) |
| Redis 가 다시 뜬 뒤 새 요청 | 6.1초 안에 201 (따로 조치 없이 복구) |

- 원인: Redis 명령 제한 시간을 설정하지 않아 Lettuce 기본값 60초다(`RedisCommandTimeoutException: Command timed out after 1 minute(s)`).
- 조회도 60초 걸린 이유: 인증 단계에서 탈퇴 회원 확인(`WithdrawnUserTokens`)이 Redis 를 읽는다. 시간 초과 뒤에는 통과시켜 200 이 나왔다.
- 저장은 인증 60초 + 처리 중 표시 60초 = 120초 뒤 실패했다.
- Redis 가 잠깐만 멈춰도 서버 스레드(최대 200)가 60초씩 묶인다. 스레드가 다 묶인 상태는 이번에 재지 않았다.

## 문제 C 개선: Redis 제한 시간 설정 (적용함)

`backend/src/main/resources/application.yaml` 에 두 줄을 넣었다. 다른 코드는 바꾸지 않았다.

```yaml
spring:
  data:
    redis:
      timeout: 2s
      connect-timeout: 2s
```

- 값의 근거: 정상일 때 Redis 명령은 수 ms 다(Redis 정상 상태 조회 1건 0.02~0.04초에 Redis 왕복이 포함된다). 2초는 그보다 훨씬 길고, 이 프로젝트의 외부 API 연결 제한(2초)과 같다.
- 고르지 않은 것: 연결이 끊겼을 때 명령을 바로 거부하는 클라이언트 옵션(Lettuce `REJECT_COMMANDS`)은 설정만으로 안 되고 코드가 필요해 넣지 않았다. 서킷 브레이커도 넣지 않았다.

같은 스크립트(`performance-tests/scripts/redis_outage.py`)로 측정용 Redis 를 멈추고 쟀다. 원본: `results/redis-outage-before.json`, `redis-outage-after.json`.

| 지표 | 설정 전 | 설정 후 | 측정 조건 |
|---|---|---|---|
| Redis 중단 중 조회(042) 1건 | 60.03초 뒤 200 | 2.02초 뒤 200 | 인증 단계의 탈퇴 확인이 시간 초과 뒤 통과 |
| Redis 중단 중 저장(041) 1건 | 120.02초 뒤 500 C014 | 4.04초 뒤 500 C014 | 인증 + 처리 중 표시, 저장된 행 0 |
| Redis 중단 중 조회 50건 동시(중앙값) | 60.05초, 모두 200 | 2.07초, 모두 200 | 서로 다른 회원 50명 |
| Redis 가 다시 뜬 뒤 새 저장이 성공하기까지 | 3.6초 | 0.2초 | 컨테이너가 PONG 을 돌려준 뒤부터 |
| Redis 정상일 때 조회 50건 동시(중앙값) | 0.05초 | 0.08초 | 참고값(정상 동작에 차이 없음) |

- 회귀 테스트: `./gradlew clean test` 2,120개 중 통과 2,110, 건너뜀 10, 실패 0.
- 한계: 전후 각 1회 실행이다(제한 시간에 걸리는 값이라 편차가 작다. "전"은 TEST 04 본 측정에서도 60.0초·120.0초로 같았다). Redis 가 **느려진** 경우(멈추지 않고 응답이 2초 넘게 걸리는 경우)는 재지 않았다. 그때는 이 설정 때문에 정상 요청이 실패할 수 있다.
- 남은 것: Redis 가 멈춰 있는 동안 조회는 2초 늦게 성공하고 저장은 실패한다. Redis 없이 저장을 받는 구조는 아니다. 문제 A·B 는 그대로다.

## 문제 A 개선: 팁 등록에 요청 키와 유일 제약 (팁 등록만 적용함)

Redis 멱등 기록이 없어져도 같은 요청 키로 팁이 또 생기지 않게 DB 가 막도록 했다.

- `V7__add_ar_tips_request_key.sql`: `ar_tips.request_key`(255자, null 허용)와 유일 제약 `(author_id, request_key)`. 기존 팁은 키가 null 이라 겹치지 않는다.
- `tip/service/TipCreateService.create`: 같은 작성자·같은 요청 키의 팁이 있으면 새로 만들지 않고 처음 팁을 돌려준다. 두 요청이 겹쳐 유일 제약에 걸리면 먼저 들어간 팁을 돌려준다.
- `TipController`: `Idempotency-Key` 값을 서비스로 넘긴다. 요청·응답·오류 코드는 그대로다.

| 지표 | 수정 전 | 수정 후 | 측정 조건 |
|---|---|---|---|
| 완료 기록 유실 뒤 같은 키로 팁 등록 | 202, 다른 tipId(100001 → 100002) | 202, 같은 tipId(104343 → 104343) | 실제 HTTP, Redis 키를 지운 뒤 재전송 |
| 저장된 팁 행 | 2 | 1 | 같은 조건 |

원본: `results/idempotency-app1.json`(전), `idempotency-after-v7.json`(후).

- 회귀 테스트: 첫 실행은 전체 2,122개 중 1개 실패(열 목록을 검사하는 `ArTipRepositoryTest` 에 새 열이 없었음). 고친 뒤 다시 돌려 2,122개 중 통과 2,112, 건너뜀 10, 실패 0.
- 정한 것: 255자를 넘는 멱등키는 DB 에 남기지 않는다(Redis 멱등 처리만 받는다). Redis 기록 없이 같은 키·다른 본문이 오면 C005 가 아니라 처음 팁을 돌려준다(DB 에 요청 해시가 없다).
- 남은 것: 나머지 26곳은 그대로다. 발자취는 재전송이 409 F003 으로 달라지는 문제가 남아 있다(수정 후에도 같은 결과). 문제 B 도 그대로다.
- Redis 제한 시간(문제 C) 적용 뒤 다시 돌린 이 실행에서, "커밋 뒤 Redis 중단" 시나리오의 처음 요청은 7.1초 뒤 201 을 받았다(전에는 60초 넘게 응답 없음). 다만 Redis 가 다시 뜬 직후 보낸 요청 1건은 4.0초 뒤 500 C014 였다. 앱이 다시 연결하기 전이라 2초 제한에 걸린 것으로 보이며, 제한 시간을 줄인 대가다.

## 해결 대안 (문제 A·B 는 적용 전, 결정 필요)

| 문제 | 대안 | 장점 | 단점 | 변경 범위 |
|---|---|---|---|---|
| C | Redis 명령·연결 제한 시간 설정(`spring.data.redis.timeout`, `connect-timeout`) | 설정 두 줄. 매달리는 시간이 60초 → 설정값 | Redis 가 느릴 때 정상 요청도 실패할 수 있어 값 선택이 필요 | 설정(전 기능 공통, 팀원 코드에도 영향) |
| A·B | 중복되면 안 되는 테이블에 "요청 키" 열과 유일 제약(예: `ar_tips (author_id, request_key)`) | Redis 와 무관하게 DB 가 막는다. 기간 제한 없음 | API 마다 열·마이그레이션·중복 시 기존 행 반환 처리가 필요 | 엔티티·마이그레이션·서비스 (API 별) |
| A·B | 멱등 기록을 DB 테이블에 두고 처리와 같은 트랜잭션으로 저장 | 한 곳에서 28곳 모두 해결 | 공통 구조를 바꿔야 하고 트랜잭션 경계를 28곳에서 맞춰야 함 | 공통 모듈 + 호출부 전체 |
| B | 처리 중 표시 수명을 늘리거나 처리 중에 연장 | 설정 변경만으로 가능 | 서버가 죽었을 때 재시도 가능해지는 시간도 같이 늘어남 | 설정 또는 공통 모듈 |
| A | 운영 Redis 영속화(appendonly)는 이미 켜져 있다(`infra/docker-compose.yml`) | 재시작으로 인한 키 유실은 줄어든다 | 완료 기록 저장 실패·30초 초과는 그대로 | 없음 |

## 주장할 수 있는 것과 없는 것

- 할 수 있음: Redis 가 정상일 때 같은 키의 반복·동시 요청은 한 번만 처리되고 같은 결과를 돌려준다(24시간).
- 할 수 없음: "정확히 한 번 처리", "영구적인 중복 방지". 완료 기록이 없거나 처리가 30초를 넘으면 다시 실행된다.

## 측정 중 알게 된 것

- 측정용 앱이 예약 작업으로 **실제 S3(개발 버킷)를 한 번 호출했다**(`S3 요청에 실패했습니다: AccessDeniedException`, 14:36). `local` 프로필의 기본 버킷 이름과 이 PC 의 AWS 기본 자격 증명으로 나간 호출이고 권한 거부로 끝나 바뀐 것은 없다. 측정 환경은 외부를 호출하지 않아야 하므로 `.env.perf` 에 없는 버킷 이름과 긴 정리 주기(365일)를 넣도록 README 를 고쳤다. 버킷 이름을 비우면 앱이 시작하지 않는다(`yeogirok.file.photo-bucket 값이 필요합니다`).
- 측정용 Redis 는 디스크에 쓰지 않는다. 운영 Redis 는 appendonly 가 켜져 있어 재시작 때 키가 남는다. 이 차이 때문에 "재시작으로 키 유실"은 운영에서 덜 일어난다.
